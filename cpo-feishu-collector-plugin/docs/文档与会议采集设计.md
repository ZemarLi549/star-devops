# cpo-feishu-collector-plugin 文档与会议采集设计

## 1. 当前结论

截至 2026-08-11，聊天采集已经跑通，文档统计和会议统计还没有正式接入。

当前状态：

- 聊天原始消息明细已经落本地 `raw-chat/`。
- 聊天聚合报告已经可生成。
- 聊天数据还没有正式写入 ES。
- 文档统计与会议统计仍是占位字段，尚未进入真实采集。

因此第 3 步的目标不是立刻把全部功能写满，而是先明确：

- 什么数据适合直接从飞书 OpenAPI 拉取
- 什么数据更适合走你已有数据库补数
- 什么数据最终进入 ES
- 什么数据只保留聚合结果

## 2. 调度方式

当前插件默认不要求用户自己维护 `crontab`。

默认方式：

- 采集器自带守护模式
- 启动后按 `17:30` 每天自动执行一次

可选方式：

- 用户也可以只跑 `--once`
- 再由系统 `crontab`、`systemd timer`、CI 调度器或运维平台托管

推荐结论：

- 个人用户侧默认走采集器内置守护
- 托管服务器批量部署时可选 `systemd`
- 不建议把默认使用方式设计成“要求每个用户自己写 crontab”

## 3. ES 状态与建议

当前还没有正式写入 ES。

现在真实数据存储位置：

- 聚合报告：`data/<userId>/latest-report.json`
- 原始聊天明细：`data/<userId>/raw-chat/*.json`

建议后续服务端分层：

- MySQL / PG：
  - 用户授权关系
  - 采集配置
  - 日报 / 周报草稿
  - 待办看板
  - 聚合统计快照
- Elasticsearch：
  - 聊天原始事件
  - 后续文档事件
  - 后续会议事件
  - AI 摘要检索素材

建议 ES 保留期：

- 原始聊天事件：15 天
- 文档事件：15 天
- 会议事件：15 天
- 聚合统计结果：180 天

原因：

- 原始事件主要服务于检索、回放、摘要和审计
- 长期报表可由关系库保留聚合结果

## 4. 文档统计设计

### 4.1 能做什么

文档侧建议分成 3 个层次：

1. 基础层
   - 时间段内新建文档数
   - 时间段内参与过的文档数
   - 文档标题列表
2. 进阶层
   - 按文档类型拆分：`doc/docx/sheet/slides/bitable`
   - 按群聊维度、所有者维度、关键词维度筛选
3. 高阶层
   - 精确编辑次数
   - 修改贡献度
   - 评论次数
   - 文档摘要

### 4.2 当前最小可用方案

先做“最小可用版本”：

- 统计用户在时间窗口内新建的文档数量
- 统计用户可见且与工作关键词相关的文档数量
- 返回文档标题、类型、所有者、文档 token

这样能先支撑：

- 首页“文档参与数量”
- 人效子系统“文档列表入口”
- AI 日报引用“今日涉及文档”

### 4.3 推荐实现路径

路径 A：飞书 OpenAPI 直接拉取

优点：

- 不依赖第三方数据库
- 用户授权链条清晰
- 插件部署简单

缺点：

- 很难只靠搜索接口精确得到“编辑次数”和“贡献度”
- 需要更多权限与更复杂的筛选策略

路径 B：飞书 API + 服务端补算

优点：

- 插件侧只负责采集轻量事件
- 服务端统一做聚合、关联、去重

缺点：

- 服务端实现复杂度更高

路径 C：直接接你们现有文档变更数据源

优点：

- 如果你们内部已有文档行为库，这会比纯 OpenAPI 更容易做“贡献度”
- 更适合长期精细化统计

缺点：

- 需要你补数源结构

当前推荐结论：

- 第一阶段用 OpenAPI 先做“新建数 + 可见文档数 + 标题列表”
- 第二阶段如果要做“编辑贡献度”，优先接你们现有文档数据源

### 4.4 文档侧权限建议

当前建议后续申请：

- `drive:drive:readonly`
- `search:docs:read`

如果要直接新建、编辑或更深度管理文档，再补：

- `docx:document`
- `docx:document:create`

### 4.5 文档侧入 ES 建议

建议文档事件 ES 结构至少包含：

- `tenantId`
- `platformUserId`
- `feishuOpenId`
- `documentToken`
- `documentType`
- `title`
- `ownerOpenId`
- `source`
- `occurredAt`
- `keywords`

## 5. 会议统计设计

### 5.1 能做什么

会议侧建议先做最容易落地的 4 个指标：

- 时间段内会议次数
- 会议总时长
- 平均会议时长
- 参会记录列表

后续可扩展：

- 组织者次数
- 参会人结构
- 会议高峰时段
- 会议纪要 / 妙记摘要
- AI 生成“会议行动项”

### 5.2 推荐实现路径

路径 A：直接走飞书会议 / 妙记接口

优点：

- 数据源统一
- 可直接接会议产物

缺点：

- 权限和接口路线会比聊天复杂
- 会议、妙记、纪要通常是多条产品线接口

路径 B：优先接你现有会议数据库

优点：

- 如果你已经有会议数据表，统计“次数 / 时长 / 参会列表”会更稳定
- 不受飞书侧接口波动影响

缺点：

- 与插件授权链路不是完全同源

当前推荐结论：

- 聊天采集继续走用户插件
- 会议统计优先接你现有会议数据库
- 如果以后要取妙记摘要、会议行动项，再补飞书会议产物接口

### 5.3 会议侧插件职责

建议不要让第一版插件硬扛所有会议统计。

插件第一版可以只保留两个职责：

- 记录用户是否启用会议统计
- 预留服务端同步入口

真正的会议明细和时长统计，更建议放服务端：

- 从你现有会议库拉
- 或从统一会议采集服务拉

### 5.4 会议侧入 ES 建议

如果后续会议事件进入 ES，建议结构至少包含：

- `tenantId`
- `platformUserId`
- `feishuOpenId`
- `meetingId`
- `topic`
- `organizerOpenId`
- `participantOpenIds`
- `startAt`
- `endAt`
- `durationMinutes`
- `source`

## 6. 平台展示建议

### 6.1 首页

首页只放纵览：

- 文档参与数量
- 新建文档数量
- 会议次数
- 会议总时长

### 6.2 AI 人效自动化系统

详情页放：

- 文档列表
- 会议列表
- 与聊天、工单关联的综合时间线
- AI 日报 / 周报草稿
- AI 待办建议

### 6.3 待办看板

后续待办来源建议支持三类：

- 聊天提及与行动语句抽取
- 会议行动项
- 文档待补充事项

## 7. 下一步建议

建议按下面顺序继续：

1. 平台后端增加聊天原始事件入 ES 能力
2. 用户表补齐 `feishu_open_id` 关联
3. 文档统计先做“新建数 + 列表”
4. 会议统计先接你现有数据库
5. 最后再做 AI 日报 / 周报 / 待办抽取

## 8. 官方参考

本设计目前已核过的飞书官方文档方向：

- 网页授权获取授权码
- `user_access_token` 获取与刷新
- IM 会话历史消息
- 云文档搜索
- 新版文档创建

说明：

- 文档相关最小可用方案基于官方云文档搜索与文档接口方向可落地
- 会议相关这里先采用“优先接你现有数据库”的保守路线，后续再补飞书会议 / 妙记官方接口细化实现
