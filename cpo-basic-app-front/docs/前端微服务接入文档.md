# cpo 前端微服务接入文档

## 1. 角色划分

`cpo-basic-app-front` 是基座，不承载每个观测领域的完整业务页面。它负责：

- 本地、SSO 或 UAP 登录模式选择
- token、刷新 token 和工作空间状态管理
- 菜单及权限初始化
- qiankun 子应用注册和路由编排
- 统一的 Axios 请求头和登录失效处理

当前子应用目录：

```text
cpo-config-front
cpo-observe-alarm-front
cpo-observe-log-front
cpo-observe-metric-front
cpo-observe-trace-front
```

旧的 `stc-observe-basic-app-front` 不再使用，也不应作为新的接入模板。

## 2. 子应用命名约定

### 2.1 工程目录

工程目录统一使用：

```text
cpo-<domain>-front
```

例如：

```text
cpo-observe-log-front
cpo-observe-metric-front
```

不要新建 `stc-*` 目录，也不要在部署脚本、容器名、文档示例中重新引入旧前缀。

### 2.2 qiankun 注册名

基座当前使用稳定的业务模块名，不直接使用工程目录名：

| 工程目录 | `moduleName` | 基座路由 |
| --- | --- | --- |
| `cpo-observe-trace-front` | `observe-trace` | `/business-observe/observe-trace` |
| `cpo-observe-metric-front` | `observe-metric` | `/business-observe/observe-metric` |
| `cpo-config-front` | `observe-config` | `/environment-config/observe-config` |
| `cpo-observe-log-front` | `observe-log` | `/business-observe/observe-log` |
| `cpo-observe-alarm-front` | `observe-alarm` | `/alarm-center/observe-alarm` |

目录重命名不会自动改变已存在的后端模块名、Nacos data-id 或运行路由。除非同时迁移所有消费者，否则保持 `moduleName` 和路由不变。

## 3. 子应用后端契约

子应用由基座登录后加载，默认依赖以下公共请求能力：

```text
请求头 token: <access-token>
请求头 Workspace-Id: <当前工作空间 ID>
```

基座在 [`src/config/axios/BaseRequest.ts`](../src/config/axios/BaseRequest.ts) 中统一注入这两个请求头。子应用应复用基座传入的 `action`、权限判断函数和模块常量，不要各自实现一套登录态。

基础认证接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `POST` | `/auth/login` | 本地账号登录 |
| `GET` | `/auth/loginMode` | 查询登录页允许的认证方式 |
| `POST` | `/auth/loginInfo` | 独立部署登录 |
| `POST` | `/auth/logout` | 注销 |
| `POST` | `/auth/refreshToken` | 刷新 token |
| `GET` | `/auth/workspace` | 查询用户工作空间 |
| `GET` | `/auth/userBaseInfo` | 查询用户基础信息 |
| `GET` | `/auth/menu` | 按工作空间查询菜单 |

## 4. 本地登录接入

`public/config.js` 的 `development.VITE_LOGIN_CONFIG.mode` 当前是 `normal`，因此本地开发走 `auth-all`，不依赖 SSO/UAP。

登录页会先请求：

```text
GET /auth/loginMode
```

返回值约定：

```json
{
  "mode": "LOCAL",
  "options": ["LOCAL"],
  "captchaEnabled": false
}
```

其中：

- `LOCAL`：只允许本地登录
- `LDAP`：只允许 LDAP 登录
- `MIXED`：前端展示本地 / LDAP 切换

前端登录逻辑位于 `src/stores/modules/user.ts`：

```ts
await userApi.login({
  account: username,
  password: loginMode === "LDAP" ? password : md5(password).toString(),
  loginMode
})
```

后端请求体最小形式：

```json
{
  "account": "admin",
  "password": "<本地登录时为MD5(明文密码)，LDAP登录时为明文密码>",
  "loginMode": "LOCAL"
}
```

当前本地验证账号为 `admin / Cxmt#666`。密码只用于开发机验证，不要写入生产环境配置、提交记录或前端代码。

登录成功后，基座从响应中保存 `tokenInfo`、用户 ID 和过期时间，并依次加载工作空间、用户信息和菜单。子应用应等待基座完成登录态初始化后再请求需要认证的接口。

## 5. 开发环境子应用地址

当前 `src/plugin/qiankun/micro-app.ts` 在 development 模式下使用以下默认入口：

| `moduleName` | 默认入口 |
| --- | --- |
| `observe-log` | `http://localhost:3004/` |
| `observe-metric` | `http://localhost:3002/` |
| `observe-trace` | `http://localhost:3001/` |
| `observe-config` | `http://localhost:3003/` |
| `observe-alarm` | `http://localhost:3005/` |

接入一个子应用至少需要：

1. 在自己的 Vite 开发服务监听对应端口。
2. 输出 qiankun 可加载的 HTML/JavaScript 入口。
3. 设置与基座一致的 history 路由基础路径。
4. 在子应用请求中携带基座传入的 `token` 和 `Workspace-Id`。
5. 通过基座约定的 `action` 与主应用同步登录、登出和路由状态。

生产或测试环境不应把地址写死在源码中。后端 `ControlApi.getDeployConfig()` 会返回 `metaList`，其中每一项包含：

```json
{
  "moduleName": "observe-log",
  "moduleUrl": "http://<host>/observe-log/"
}
```

基座会按 `moduleName` 匹配并注册对应 `moduleUrl`。如果 `moduleUrl` 是 Base64 编码，基座会先解码再注册。

## 6. 代理和服务边界

开发代理位于 [`vite.config.ts`](../vite.config.ts)，主要规则如下：

| 前端路径 | 默认后端 |
| --- | --- |
| `/auth` | `http://127.0.0.1:9004/` |
| `/graphql` | `http://127.0.0.1:9004/` |
| `/api/n9e` | `http://127.0.0.1:9004/` |
| `/log-platform` | `http://127.0.0.1:9004/` |
| `/alarm-manager` | `http://127.0.0.1:9004/` |
| `/alarm-chain` | `http://127.0.0.1:9004/` |
| `/aiops/resource` | `http://127.0.0.1:9004/` |
| `/nodeman` | `http://127.0.0.1:8091/`，并移除 `/nodeman` 前缀 |

`auth-all` 目前只保证认证和基础用户接口。`/graphql`、告警统计、日志平台等路径需要后续对应后端微服务提供实现；只启动认证服务时，这些首页请求返回 `404` 属于预期的缺少服务状态。

## 7. 子应用启动检查清单

新增或迁移 `cpo-*` 子应用时，按以下顺序检查：

- 工程目录名称使用 `cpo-` 前缀。
- `package.json`、部署脚本和容器配置不引用旧 `stc-` 工程名。
- 子应用入口可以被 qiankun 从 `moduleUrl` 访问。
- 子应用的静态资源路径在挂载到非根路径时仍然正确。
- 子应用路由与基座 `activeRule` 一致。
- 登录后请求携带 `token` 和 `Workspace-Id`。
- 注销后停止轮询、清理页面状态并返回基座登录页。
- 基座独立刷新和子应用切换都没有重复注册 qiankun 应用。

## 8. 接口调试示例

先通过浏览器登录，或通过接口取得 token。随后将 token 和工作空间 ID 替换到请求中：

```bash
curl -sS \
  -H 'token: <access-token>' \
  -H 'Workspace-Id: <workspace-id>' \
  http://127.0.0.1:9004/auth/menu
```

不要把真实 token 写入源码、文档或 shell 脚本。接口返回 `401` 时，优先检查 token 是否过期；返回 `403` 时，检查工作空间和菜单权限；返回 `404` 时，检查对应业务后端是否启动以及 Vite proxy 是否指向正确服务。

## 9. 后续微服务化边界

后续重构建议保持以下边界：

```text
auth-all
  负责身份认证、token、工作空间、菜单和权限基础能力

cpo-basic-app-front
  负责基座布局、登录态、路由、微应用注册和公共请求约定

cpo-observe-*-front
  负责单一观测领域页面和领域接口调用

observe-* 后端微服务
  负责领域数据查询、写入和领域任务，不在前端保存凭据
```

先迁移接口契约和运行配置，再做目录、包名、容器名和 Nacos data-id 的规范化；目录前缀改为 `cpo-` 不应直接改动已有 API 路径和 `moduleName`。

## 10. 用户身份扩展与 LDAP 备用接入

用户管理前端当前维护以下扩展字段：

```text
feishuUserId
itWorkbenchUserId
identitySource
```

其中 LDAP 用户不再单独录入 `ldapAccount`，后端在 `identitySource=LDAP` 时自动复用 `account`。当前 `auth-all` 已支持这些字段在 `sys_user` 中直接落库，并通过用户列表与 `userBaseInfo` 返回。后续如果一个用户需要绑定多个外部身份，再演进到独立身份表。详细设计见：

- [`用户身份与LDAP接入设计.md`](./用户身份与LDAP接入设计.md)

LDAP 必须作为租户级或平台级备用登录能力由后端接管，前端不保存 bind password，不直连 LDAP 服务，只展示配置状态和映射结果。

## 11. 工作台个人运营总览

工作台首页新增“个人运营总览”区域，服务于以下聚合数据：

- 个人处理工单数、已办和协办情况。
- 飞书单聊、群聊、被 `@` 次数。
- 参与文档和会议数量。
- 个人负责的应用系统和资源数量。
- 个人机器、内存、磁盘和异常概览。

建议使用统一聚合接口：

```text
GET /api/workbench/overview?startAt=&endAt=&timeZone=
```

详情入口建议保持稳定业务路由：

```text
/work-order-ops
/cmdb-resource-ops
/zabbix-center
/assistant
/productivity
```

工单 PostgreSQL、CMDB、多个 Zabbix 数据中心和 `zabbix-watcher` 的接入设计见：

- [`工单与资源总览接入设计.md`](./工单与资源总览接入设计.md)
