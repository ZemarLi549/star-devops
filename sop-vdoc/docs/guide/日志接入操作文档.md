## 接入前置条件

日志接入的所有功能都是在应用维度的基础上进行配置的, 在进行日志接入时,需要在星际系统的 `用户权限管理-空间管理`菜单下, 
选择一个数据单元创建应用, 具体操作可以参考 `空间管理` 操作文档

接入方式分为 `在线接入` 和 `离线接入` , 分别对应不用的业务场景
- 在线接入: 用户在日志接入配置页面, 进行日志采集路径等属性的配置, 星际系统将这些配置属性自动下发到对应机器的日志采集器, 不需用户感知, 通过页面操作
  就可以完成整个接入流程
- 离线接入: 用户对日志采集有定制的配置需求, 需要用户对日志采集器Vector比较熟悉, 可自行配置日志采集器

在线接入的前置条件是需要在星际系统的`环境配置`功能安装Agent和日志采集插件st-vector, 具体操作可以参考`环境配置`操作文档
在线接入和离线接入都可以通过在页面进行字段映射配置进行数据保存

一句话总结: 在线接入是星际系统负责管理日志采集插件的配置, 离线接入是用户手动维护日志采集器的配置

请根据以上描述, 选择合适的接入方式。

## Nginx访问日志接入文档

Nginx访问日志接入可以快速的接入Nginx的access日志, 同时提取了常用的nginx字段, 整合了Nginx监控仪表盘 

### 修改Nginx的配置文件

离线接入和在线接入都必须要先修改 Nginx 的配置文件，实现两个功能：

- 配置 Nginx 的 access.log 的日志输出格式
- 实现 access.log 和 error.log 按天切割，过期删除（比如只保存最近7天的日志）

打开 Nginx 的配置文件 `nginx.conf` , 修改 log_format 日志格式和日志存储路径。 注意，log_format 后面的 main 需要和 access_log 最后的 main 相同, 且 log_format 的配置必须在配置日志存储路径的上方：

![nginx_1.png](imgs/log/log_access/nginx_1.png)

log_format 和日志存储路径的详细内容为：

```
# 修改access.log的输出格式(必须这样写，不能人为修改)
log_format main '{"http_referer":"$http_referer","remote_addr":"$remote_addr","remote_user":"$remote_user","request_uri":"$request_uri","request_length":"$request_length","request_time":"$request_time","request_method":"$request_method","upstream_addr":"$upstream_addr","upstream_response_time":"$upstream_response_time","http_user_agent":"$http_user_agent","http_x_forwarded_for":"$http_x_forwarded_for","status":"$status","time_local":"$time_iso8601","body_bytes_sent":"$body_bytes_sent","bytes_sent":"$bytes_sent","connection":"$connection","host":"$host","uri":"$uri"}';

# 配置access.log和error.log的日志存储路径（可以自定义存储路径，error.log 的日志级别warn也可根据需求修改）
access_log /data/nginx/nginxServer-1.15.9/logs/access.log main;  # 访问日志
error_log /data/nginx/nginxServer-1.15.9/logs/error.log warn;    # 错误日志
```

使用修改后的配置文件启动 Nginx，使用命令： `nginx -s reload`, 重新加载配置

实现日志切割和过期删除前，需要确保系统有 `logrotate` 环境，使用命令检查是否安装 `logrotate` ：

````shell
rpm -qa | grep logrotate   # centos；基于 RPM 包的麒麟版本
dpkg -l | grep logrotate   # Ubuntu；基于 Debian 包的麒麟版本
````

应出现的结果 logrotate 的版本 ，如若没有 `logrotate` 的环境，需要自行安装后再进行后续的操作。

在 `/etc/logrotate.d/` 目录下为 Nginx 创建一个新的名为 `nginx` 配置文件：

````shell
# 创建一个新的 nginx 配置文件，用于实现日志按天切割和过期删除：
touch /etc/logrotate.d/nginx
vim /etc/logrotate.d/nginx
````

logrotate 的 `nginx` 配置文件的内容如下：

````
# 需要配置为自己的access.log日志存储路径
/data/nginx/nginxServer-1.15.9/logs/access.log {
    daily                   
    missingok                         
    compress                
    delaycompress          
    notifempty                
    dateext                
    dateformat -%Y-%m-%d    
    sharedscripts          
    postrotate
        # 日志路径需要配置成自己的
        mv /data/nginx/nginxServer-1.15.9/logs/access.log-$(date +\%Y-\%m-\%d) /data/nginx/nginxServer-1.15.9/logs/access-$(date +\%Y-\%m-\%d).log
        # 需要配置为自己的nginx.pid
        if [ -f /data/nginx/nginxServer-1.15.9/logs/nginx.pid ]; then
            kill -USR1 `cat /data/nginx/nginxServer-1.15.9/logs/nginx.pid`
        fi
    endscript
}

# 需要配置为自己的error.log日志存储路径
/data/nginx/nginxServer-1.15.9/logs/error.log {
    daily                   
    missingok                             
    compress                
    delaycompress          
    notifempty              
    dateext                
    dateformat -%Y-%m-%d    
    sharedscripts          
    postrotate
        # 日志路径需要配置成自己的
        mv /data/nginx/nginxServer-1.15.9/logs/error.log-$(date +\%Y-\%m-\%d) /data/nginx/nginxServer-1.15.9/logs/error-$(date +\%Y-\%m-\%d).log
        # 需要配置为自己的nginx.pid
        if [ -f /data/nginx/nginxServer-1.15.9/logs/nginx.pid ]; then
            kill -USR1 `cat /data/nginx/nginxServer-1.15.9/logs/nginx.pid`
        fi
    endscript
}
````

编辑好的 logrotate 的 `nginx` 配置文件，使用如下命令测试：

````shell
sudo logrotate -f /etc/logrotate.d/nginx
````

执行命令无报错，并且能在 nginx 的日志目录下查看到格式为 `access-yyyy-MM-dd.log` 和 `error-yyyy-MM-dd.log` 的文件，即成功实现日志切割。

由于使用 logrotate 修改了日志文件格式，所以需要使用 cron 表达式，定时执行任务：

````shell
# 编辑 crontab 配置文件：
crontab -e
# 每天 2 点执行任务(替换日志存储路径)：
0 2 * * * find /data/nginx/nginxServer-1.15.9/logs/ -type f -name "access-*.log" -mtime +7 -exec rm -f {} \;
0 2 * * * find /data/nginx/nginxServer-1.15.9/logs/ -type f -name "error-*.log" -mtime +7 -exec rm -f {} \;
````

即成功实现日志过期删除策略。

首先列出几种常见日志格式的样例和对应的正则式

日志示例1：

pattern："%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{50} L%line - %msg %n"

```text
2024-07-02 15:45:55.233 [http-nio-8100-exec-4] INFO  c.i.i.o.l.controller.LogAnalysisController L37 - 查询日志时间分布请求参数: applicationCode:sdk_log_1, type:LQL, query:, startTime:1569859200, endTime:1719906346

FROM log_record_sdk_log_1
WHERE
	AND log_date >= '2019-10-01 00:00:00.000'
	AND log_date <= '2024-07-02 15:45:46.000'
ORDER BY log_date DESC
LIMIT 0, 20
```

```text
行首匹配正则：^\d{4}-\d{2}-\d{2}\s\d{2}:\d{2}:\d{2}\.\d{3}\s+\[.*\]\s+
```

## 主机审计日志接入文档
auditd 是 Linux 系统中的审计守护进程，用于记录系统的审计日志。它可以监控和记录系统中的各种活动，如文件访问、系统调用、用户登录等

主机审计日志接入可以快速的接入服务器的审计日志, 提取用户登录、用户操作事件以及常用的字段，用以追踪用户登录及执行的操作

由于linux系统的原始审计日志类型繁多，不同类型的日志字段也不同，接入之前需要先配置`auditd`和`laurel`，
对原始日志进行处理， 提取出需要的日志和常用的字段，方便后续的检索和分析。
### 修改auditd配置

centos7及openEuler 22默认已安装audit，执行命令`systemctl status auditd.service`查看auditd服务是否开启：
![linux_audit_1.png](imgs/log/linux_audit/linux_audit_1.png)

确认auditd服务开启后，修改auditd配置文件：`/etc/audit/rules.d/audit.rules`,添加如下内容：
`-a always,exit -F arch=b64 -S execve -k exec_commands`用以记录用户操作日志
```shell 
## First rule - delete all
-D

## Increase the buffers to survive stress events.
## Make this bigger for busy systems
-b 8192

## Set failure mode to syslog
-f 1

# 记录用户操作信息
-a always,exit -F arch=b64 -S execve -k exec_commands
```

## 日志数据清理
### Doris数据清理

在进行日志接入时可以选择日志保留时间（天）：

![image.png](imgs/log/log_access/日志保留时间.png)

过期日志将被清除，**建议根据实际情况进行评估后合理设置日志保留天数，避免手动清除数据**。

若因为特殊原因必须手动清理doris存储的日志数据，建议按照以下方式进行

由于日志数据表（命名方式为：`log_record_applicationCode`）开启了自动分区，且默认按天进行分区，数据清理时建议删除特定某天对应的分区
需要注意的是，doris禁止在开启动态分区时手动删除或者添加分区，因此要先关闭动态分区，手动删除分区之后再开启。

```shell
 [HY000][1105] errCode = 2, detailMessage = Cannot add/drop partition on a Dynamic Partition Table, Use command `ALTER TABLE log_record_test SET ("dynamic_partition.enable" = "false")` firstly.
```

以下以表`log_record_test`为例：

```sql
# 关闭自动分区
ALTER TABLE log_record_test SET ("dynamic_partition.enable" = "false");
# 查看log_record_test表的分区
SHOW PARTITIONS FROM log_record_test;

# 删除指定分区
ALTER TABLE table_name DROP PARTITION partition_name;

# 重新开启自动分区
ALTER TABLE log_record_test SET ("dynamic_partition.enable" = "true");
# 查看是否成功开启自动分区
SHOW DYNAMIC PARTITION TABLES;
```

注意，如果设置了创建指定天数的历史分区且又再次开启了自动分区，如：

```sql
"dynamic_partition.history_partition_num" = "7"
```

当删除的分区在这个范围内，比如今天是1月10日，手动删除了1月7日的分区，在指定的历史分区内，doris会自动重新创建这个分区，但是分区内的数据不会恢复。

### kafka数据清理

#### kafka的日志

日志的英语是“log”，但Kafka的数据文件也被称为log，所以很多时候会造成一定的歧义。在Kafka中，日志分为两种：

- 操作日志
- 数据日志

其中操作日志就是我们一般认为的日志，由`$KAFKA_HOME/config/log4j.properties`管理

**数据日志是指Kafka的topic中存储的数据**，这种日志是在`$KAFKA_HOME/config/server.properties`文件中配置，配置项为log.dirs，默认为`/tmp/kafka-logs`，建议改成非tmp路径


#### 数据日志自动清理（推荐）

kafka有两种数据日志清理策略：

```properties
log.cleanup.policy=compact
log.cleanup.policy=delete
```

其中compact策略只能支持键值对存储的数据，delete则没有这个限制

1. 若存储数据为键值对，建议设置数据日志清理配置如下：

```properties
# $KAFKA_HOME/config/server.properties
# 开启压缩策略                                            
log.cleaner.enable=true
log.cleanup.policy=compact,delete
# 日志保留时间
log.retention.hous=168
# 按天滚动（segment生成）
log.roll.hours=24
```

注意设置的清理策略为`compact,delete`，因为若只设置`compact`只能保证同一个`key`仅保留最新的数据，但超期的`key`不会被清理，如果不停有`key`新增，仍会导致磁盘打满

2. 若存储数据不为键值对，建议设置数据日志清理配置如下：

```properties
# $KAFKA_HOME/config/server.properties
# 开启删除策略                                            
log.cleanup.policy=delete
# 日志保留时间
log.retention.hous=168
# 按天滚动（segment生成）
log.roll.hours=24
```

过期数据会被自动清理

**建议根据实际情况进行评估后合理设置日志在kafka中的保留时间（默认为7天），避免手动清除数据**



#### 手动清理topic部分数据

若因为特殊原因必须手动清理部分数据，建议采用以下方案

- 1.首先查看日志服务消费者组`log-consumer`的偏移量：

```shell
[root@cassandra kafka_2.13-2.8.2]./bin/kafka-consumer-groups.sh --describe --bootstrap-server <host_ip>:9092 --group log-consumer

GROUP           TOPIC            PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG             CONSUMER-ID                                                  HOST            CLIENT-ID
log-consumer    log_record_topic 0          1221306201      1221306201      0               consumer-log-consumer-1-4b0b4c23-b294-4471-9c4b-91e57bc3a801 /172.31.65.35   consumer-log-consumer-1
log-consumer    log_record_topic 1          1183324008      1183324008      0               consumer-log-consumer-1-4b0b4c23-b294-4471-9c4b-91e57bc3a801 /172.31.65.35   consumer-log-consumer-1
log-consumer    log_record_topic 2          1170516043      1170516043      0               consumer-log-consumer-1-b719318b-a278-48d4-b589-5e08d345d602 /172.29.247.156 consumer-log-consumer-1
```

`CURRENT-OFFSET` 为当前消费者组在对应分区的偏移量，`LAG`为积压量

- 2.可以将topic中已消费的记录（`CURRENT-OFFSET` 前的记录）清除，在`$KAFKA_HOME`执行以下命令：

```shell
[root@cassandra kafka_2.13-2.8.2]./bin/kafka-delete-records.sh --bootstrap-server <host_ip>:9092 --offset-json-file offsets.json

Executing records delete operation
Records delete operation completed:
partition: log_record_topic-2   low_watermark: 1170516043
partition: log_record_topic-0   low_watermark: 1221306201
partition: log_record_topic-1   low_watermark: 1183324008
```

命令解释：

- `./bin/kafka-delete-records.sh`：kafka提供的记录清理脚本
- `--bootstrap-server 172.30.14.135:9092` ：指定kafka服务主机host与端口
- `--offset-json-file offsets.json`：通过`offsets.json`指定需要清理的主题、分区及偏移量，具体内容见后

执行成功后的响应`low_watermark`表示删除数据后剩余最老记录的偏移量

**offsets.json**文件指定主题、分区、偏移量:

```json
{
    "partitions": [
      {
        "topic": "log_record_topic",
        "partition": 0,
        "offset": 1221306201
      },
      {
        "topic": "log_record_topic",
        "partition": 1,
        "offset": 1183324008
      },
      {
        "topic": "log_record_topic",
        "partition": 2,
        "offset": 1170516043
      }
    ]
  }
```

- **`topic`**: 主题名称，指定从哪个主题删除记录。
- **`partition`**: 分区号，指定从哪个分区删除记录。
- **`offset`**: 偏移量，指定从哪个偏移量开始删除记录；所有小于这个偏移量的记录将被删除，若offset比最旧的数据offset还小则不会生效，此处指定为消费者组已消费的偏移量，将已消费的全部清理。offset填写-1意味着topic分区数据全删除。
