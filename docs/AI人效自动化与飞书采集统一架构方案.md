# AI人效自动化与飞书采集统一架构方案

更新时间：2026-08-11

## 1. 目标

本方案用于落地以下统一能力：

- 用户侧飞书聊天采集
- 服务端统一接收与归档
- Elasticsearch 原始事件检索
- Elasticsearch 最终统计与自由分析
- AI 日报 / 周报生成
- AI 事项抽取与待办生成
- 后续待办看板生成
- 文档统计与会议统计扩展

## 2. 整体架构

```text
用户本机 / 托管机器
  └─ cpo-feishu-collector-plugin
      ├─ 用户 OAuth 授权
      ├─ 本地过滤
      ├─ 本地 raw-chat 落盘
      ├─ 本地 latest-report 落盘
      └─ 上传到 AI 人效服务

服务端
  └─ cpo-ai-productivity-service
      ├─ 接收插件上报
      ├─ 本地事件归档
      ├─ 写入 Elasticsearch
      ├─ 聚合统计接口
      ├─ AI 事项抽取接口
      ├─ AI 日报生成接口
      └─ 后续待办看板接口

数据层
  ├─ Elasticsearch
  │   ├─ 聊天原始事件
  │   ├─ 最终统计结果
  │   ├─ AI 事项抽取结果
  │   ├─ AI 日报 / 周报摘要
  │   ├─ 后续文档原始事件
  │   └─ 后续会议原始事件
  ├─ MySQL
  │   ├─ 用户表
  │   ├─ 组织 / 部门关系
  │   ├─ 飞书身份映射
  │   └─ LDAP / 本地账号映射
  └─ Nacos
      └─ 通用配置中心
```

## 2.1 组织级独立部署原则

后续扩展到全公司时，推荐按组织 / 部门独立部署空间：

- 每个组织可独立部署一套 `cpo-ai-productivity-service`
- 每个组织可独立使用一套 ES 集群，或在共享 ES 中使用独立 index 前缀
- 全公司统一复用一套 MySQL 用户表
- 平台统一维护空间注册表
- 用户切换空间时，调用对应空间的后端
- 当前默认先使用内置空间

这样做的目标是：

- 业务统计和 AI 摘要按组织隔离
- 用户主数据统一
- 不同组织可独立扩容、独立保留数据、独立做权限治理

## 2.2 空间注册模型

建议平台维护一张“空间注册表”，每个空间至少记录：

- `spaceId`
- `spaceName`
- `organizationId`
- `departmentId`
- `backendBaseUrl`
- `gatewayRoutePrefix`
- `elasticsearchClusterName`
- `elasticsearchBaseUrl`
- `status`
- `isBuiltin`

调用原则：

- 默认进入内置空间
- 用户切换空间时，前端 / 网关根据 `spaceId` 路由到对应后端
- 各空间后端只处理本空间采集、统计、事项、日报等业务数据
- MySQL 用户表继续作为共享身份源，不随空间重复建设

## 3. 当前已落地能力

截至 2026-08-11，已完成：

- 飞书 OAuth 用户授权
- `user_access_token` 自动刷新
- 最近 `N` 天聊天采集
- 机器人 / 审批 / 通知 / 系统模板消息过滤
- 群聊名称、群聊名称正则、群 ID 过滤
- `raw-chat` 原始消息明细落盘
- `latest-report` 聚合报告落盘
- AI 人效服务上传接收骨架
- 前端首页服务入口与个人运营拆分
- 服务端 ES 原始事件落库能力
- 服务端最终统计入 ES 的架构方向已确认

## 4. 数据分层

### 4.1 原始事件

存储位置：

- 当前本地：`cpo-feishu-collector-plugin/data/<userId>/raw-chat/*.json`
- 目标服务端：Elasticsearch

用途：

- 检索
- 明细回放
- 时间窗口分析
- AI 日报 / 周报 / 待办提取

### 4.2 聚合统计

存储位置：

- 当前本地：`latest-report.json`
- 目标服务端：Elasticsearch 汇总索引

用途：

- 首页纵览
- 统计大盘
- 用户分析页
- 人效趋势分析
- 事项统计与待办抽取上游输入

### 4.3 AI 产物

存储位置：

- `cpo-ai-productivity-service/data/ai-summary/...`
- 后续统一进入 Elasticsearch

用途：

- 日报
- 周报
- 待办建议

### 4.4 事项统计

事项统计是后续很关键的一层，不只看消息次数，而是要把：

- 聊天
- 会议
- 文档
- AI 抽取事项

统一汇总。

存储位置建议：

- Elasticsearch `action-items` 索引

用途：

- 个人事项清单
- AI 待办看板
- 日报 / 周报中的行动项汇总
- 管理员横向分析

## 5. 保留策略

默认策略：

- 原始事件：15 天
- 聚合统计：180 天
- AI 日报 / 周报：建议至少 180 天

说明：

- 原始事件以 ES 为主，便于短期检索
- 最终统计也进入 ES，便于长期趋势分析和自由聚合
- 每个空间自行维护 ES 生命周期和历史清理
- 公共平台不跨空间执行删除

详细规则见：

- `docs/AI人效空间数据清理与保留策略.md`

## 6. 用户关联策略

当前飞书聊天最稳定的用户标识是：

- `open_id`

当前插件已输出：

- `participants[].feishuOpenId`
- `events[].senderOpenId`
- `events[].mentionedOpenIds`

平台用户表建议至少保留：

- `feishu_open_id`
- `account`
- `real_name`
- `employee_no`
- `third_workbench_id`
- `department_id`
- `organization_id`

后端统一按 `feishu_open_id` 做关联回填。

说明：

- 共享 MySQL 用户表只承载身份主数据
- 各组织自己的人效统计、AI 摘要、事项结果不回写共享用户表

## 9. 多组织扩展建议

后续全公司推广时，建议按下面的边界建设：

### 9.1 共享层

- MySQL 用户表
- `auth-all`
- 公共登录 / LDAP 能力

### 9.2 组织独立层

- `cpo-ai-productivity-service`
- Elasticsearch
- 采集结果索引
- AI 摘要索引
- 事项索引
- 组织自己的通知策略

### 9.3 组织隔离字段建议

- `organizationId`
- `departmentId`
- `spaceId`
- `platformUserId`
- `feishuOpenId`

### 9.4 空间切换建议

- 平台首页或个人运营入口显示当前空间
- 默认使用 `builtin` 内置空间
- 切换空间后：
  - 采集结果查询走目标空间后端
  - AI 日报生成走目标空间后端
  - 事项统计也走目标空间后端
  - 通知查询走目标空间后端

这样可以把大体量数据按空间拆开，而不是所有查询都落在一套后端上

### 9.5 空间清理责任

- 用户本地采集器只清理本地缓存
- 空间后端只清理本空间临时数据
- 空间 ES 只清理本空间索引
- 内置空间也按独立空间维护清理任务

## 10. 近期实施顺序

建议顺序：

1. 聊天原始事件正式写入 Elasticsearch
2. 最终统计结果正式写入 Elasticsearch
3. 平台用户表按 `open_id` 关联回填
4. 聊天 + 会议 + 文档事项抽取
5. 聊天分析统计接口
6. AI 日报 / 周报展示
7. 待办看板
8. 文档统计
9. 会议统计
