# 生产部署-后端微服务部署

更新时间：2026-08-18

## 1. 文档目标

本文用于规范 `star-devops` 当前后端微服务的生产部署方式，覆盖以下组件：

- `auth-all`
- `cpo-ai-productivity-service`
- `AstrBot`
- 可选 `cpo-api-gateway`

本文只描述后端服务部署，不展开前端静态站点和中间件细节：

- 微前端与 `Nginx` 见《生产部署-微前端Nginx配置部署》
- `MySQL`、`Redis`、`Nacos`、`Elasticsearch` 等见《生产部署-中间件二进制部署》

## 2. 当前服务边界

### 2.1 auth-all

- 技术栈：`Java 8 + Spring Boot`
- 职责：统一登录、用户、菜单、工作空间、微应用 `meta` 元数据
- 配置方式：运行时直接从 `Nacos` 拉取
- 当前关键配置坐标：
  - namespace：`st-observable`
  - group：`auth-all`
  - dataId：`application.yaml`

### 2.2 cpo-ai-productivity-service

- 技术栈：`Python 3 + Tornado`
- 职责：AI 人效自动化系统后端 API、飞书采集汇总、日报生成、AstrBot 调用
- 当前配置方式：
  - 进程读取本地 `config/application.yaml`
  - 环境变量可覆盖
  - 配置源统一约定由 `Nacos` 管理，但当前服务本身不直接通过 SDK 热拉取配置
- 生产建议：
  - 部署流程从 `Nacos` 渲染配置到本地文件
  - 或由 `systemd` 注入环境变量

### 2.3 AstrBot

- 技术栈：独立 Python 服务
- 职责：承接 AI 模型调用、日报/周报/事项抽取
- 生产关系：
  - `cpo-ai-productivity-service` 通过 HTTP 调用 AstrBot
  - 模型密钥和模型路由仅放 AstrBot 服务端，不下发前端

### 2.4 cpo-api-gateway

- 技术栈：`KrakenD CE`
- 职责：统一 API 入口、限流、超时、熔断、路径路由
- 当前状态：可选组件，不强依赖
- 生产建议：优先使用官方二进制运行

## 3. 推荐拓扑

```text
浏览器
  |
  v
Nginx / LB
  ├─ /auth/                    -> auth-all
  ├─ /productivity-api/        -> cpo-ai-productivity-service
  ├─ /api/astrbot/             -> AstrBot 或 cpo-api-gateway
  └─ 其他业务路径               -> 现网后端

Nacos
  ├─ auth-all/application.yaml
  ├─ cpo-ai-productivity-common.yaml
  ├─ cpo-feishu-collector-plugin.yaml
  └─ 其他服务 dataId

存储与依赖
  ├─ MySQL                     -> auth-all、Nacos
  ├─ Redis                     -> auth-all
  ├─ Elasticsearch             -> 人效原始事件/摘要/事项
  ├─ PostgreSQL                -> 外部工单库
  └─ AstrBot                   -> AI 摘要生成
```

## 5. 配置中心约定

### 5.1 统一原则

- 通用配置统一维护在 `Nacos`
- 敏感配置只放服务端，不放前端构建产物
- 生产部署不直接手改仓库中的示例配置文件
- 实际运行配置优先来自：
  1. `Nacos`
  2. 机密管理系统
  3. `systemd Environment`
  4. 本地渲染后的 `application.yaml`

### 5.2 建议 dataId 划分

```text
auth-all / application.yaml
cpo-ai-productivity-common.yaml
cpo-feishu-collector-plugin.yaml
cpo-astrbot-adapter.yaml
```

### 5.3 当前真实差异

- `auth-all`：已经按标准 `Nacos` 方式启动
- `cpo-ai-productivity-service`：当前仍是“由部署流程渲染配置到本地文件后再启动”

因此生产文档里必须区分两种配置加载方式，不能把全部服务都写成“已直接热加载 Nacos”。

## 6. auth-all 生产部署

### 6.1 部署前检查

- 已准备 `JDK 8`
- 已准备 `Nacos`
- 已在 `Nacos` 中创建 namespace：`st-observable`
- 已导入 `group=auth-all`、`dataId=application.yaml`
- `MySQL`、`Redis` 已可达

### 6.2 发布包结构

生产建议使用已经解压好的标准目录，而不是直接从源码目录运行：

```text
/data/apps/star-devops/auth-all/
  auth-all.jar
  config/bootstrap.yml
  lib/*
  logs/
  run.sh
```

仓库内参考结构：

```text
auth-all/pack/
auth-all/starter/target/auth-all/
```

### 6.3 关键环境变量

```bash
export CONFIG_NACOS_SERVER_ADDR=127.0.0.1:8848
export CONFIG_NACOS_USERNAME=nacos
export CONFIG_NACOS_PASSWORD='replace-me'
export CONFIG_NACOS_NAMESPACE=st-observable
export AUTH_NACOS_SERVER_GROUP=auth-all
```

### 6.4 bootstrap.yml 要点

`auth-all/config/bootstrap.yml` 只保留配置中心入口，不把业务配置写死在本地：

```yaml
auth:
  nacos:
    server-addr: ${CONFIG_NACOS_SERVER_ADDR:127.0.0.1:8848}
    username: ${CONFIG_NACOS_USERNAME:nacos}
    password: ${CONFIG_NACOS_PASSWORD:nacos}
    namespace: ${CONFIG_NACOS_NAMESPACE:st-observable}
spring:
  cloud:
    nacos:
      config:
        file-extension: yaml
        extension-configs[0]:
          group: ${AUTH_NACOS_SERVER_GROUP:auth-all}
          data-id: application.yaml
```

### 6.5 Nacos 中必须确认的业务配置

最少确认以下内容：

- `server.port`
- `server.servlet.context-path=/auth`
- `nginx.url`
- `authentication.login-mode`
- `spring.redis.*`
- `spring.datasource.*`
- `deploy_mode`
- `inner.auth.excludeUrls`
- `inner.apiPermission.excludeUrls`

特别注意：

- `nginx.url` 必须配置为门户对外地址，例如 `https://portal.example.com`
- 它会影响 `auth-all` 返回的 `/auth/meta` 微应用地址

### 6.6 启动方式

直接启动：

```bash
cd /data/apps/star-devops/auth-all
sh run.sh start
```

如果不使用 `run.sh`，可直接执行：

```bash
cd /data/apps/star-devops/auth-all
java -jar auth-all.jar
```

### 6.7 systemd 建议

文件：`/etc/systemd/system/auth-all.service`

```ini
[Unit]
Description=auth-all
After=network.target

[Service]
Type=simple
User=starops
Group=starops
WorkingDirectory=/data/apps/star-devops/auth-all
Environment=CONFIG_NACOS_SERVER_ADDR=127.0.0.1:8848
Environment=CONFIG_NACOS_USERNAME=nacos
Environment=CONFIG_NACOS_PASSWORD=replace-me
Environment=CONFIG_NACOS_NAMESPACE=st-observable
Environment=AUTH_NACOS_SERVER_GROUP=auth-all
ExecStart=/usr/bin/java -jar /data/apps/star-devops/auth-all/auth-all.jar
SuccessExitStatus=143
Restart=always
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

启停命令：

```bash
systemctl daemon-reload
systemctl enable auth-all
systemctl start auth-all
systemctl status auth-all --no-pager
```

### 6.8 验收

```bash
curl -s http://127.0.0.1:9004/auth/loginMode
curl -s http://127.0.0.1:9004/auth/actuator/health
```

登录成功后，再检查：

- `/auth/workspace`
- `/auth/userBaseInfo`
- `/auth/menu`
- `/auth/meta`

如果 `ai-productivity` 没出现在 `/auth/meta`，需要检查：

- `sys_config` 中是否存在 `DEPLOY_MODULE=ai-productivity`
- 类路径下是否存在 `menuAndMetaInfo/ai-productivity.json`
- 是否执行过：

```bash
curl -X POST http://127.0.0.1:9004/auth/metaAndMenu/ai-productivity
```

## 7. cpo-ai-productivity-service 生产部署

### 7.1 部署前检查

- 已安装 `Python 3`
- 已准备 `Nacos`
- 已准备 `Elasticsearch`
- 已准备 `AstrBot`
- 如需工单数据，外部 `PostgreSQL` 已可达

### 7.2 当前配置策略

当前服务配置文件位置：

```text
cpo-ai-productivity-service/config/application.yaml
```

仓库示例文件：

```text
cpo-ai-productivity-service/config/application.example.yaml
```

当前版本推荐做法：

1. 通用配置存放在 `Nacos`
2. 发布流程将 `Nacos` 配置渲染到 `config/application.yaml`
3. 敏感值通过环境变量覆盖

### 7.3 关键配置项

至少确认以下项：

- `server.port=9060`
- `datasource.workorder-pg.*`
- `storage.raw-retention-days=15`
- `storage.summary-retention-days=180`
- `elasticsearch.*`
- `collector.data-root`
- `astrbot.base-url`
- `astrbot.api-key`
- `reporting.default-user-id`
- `notification.webhook-url`

### 7.4 虚拟环境初始化

```bash
cd /data/apps/star-devops/cpo-ai-productivity-service
python3 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install -r requirements.txt
```

如果直接使用仓库脚本：

```bash
cd /home/kali/ai_study/star-devops
bash scripts_dir/bootstrap-python-service.sh cpo-ai-productivity-service
```

### 7.5 启动方式

前台启动：

```bash
cd /data/apps/star-devops/cpo-ai-productivity-service
CONFIG_FILE=/data/apps/star-devops/cpo-ai-productivity-service/config/application.yaml \
  .venv/bin/python app.py
```

```bash

setsid env CONFIG_FILE=/data/apps/star-devops/cpo-ai-productivity-service/config/application.yaml \
  .venv/bin/python app.py >> logs/service.out 2>&1 < /dev/null &
```

## 8. AstrBot 生产部署

### 8.1 部署原则

- AstrBot 独立部署，不与 `cpo-ai-productivity-service` 混跑
- 模型密钥仅保存在 AstrBot 服务端
- 通过内网地址供人效服务调用

### 8.2 目录建议

```text
/data/apps/star-devops/AstrBot/
├─ data/
├─ logs/
├─ config/
└─ .venv/
```

### 8.3 对 cpo-ai-productivity-service 的影响项

需要在人效服务配置中正确设置：

```yaml
astrbot:
  base-url: http://127.0.0.1:6185
  api-key: replace-me
  username: productivity-bot
  config-id: default
  selected-provider: deepseek
  selected-model: deepseek-v4-flash
```

### 8.4 验收

- AstrBot 自身健康检查正常
- 人效服务可以成功调用日报生成接口
- 失败时能通过通知渠道写入失败事件

## 9. cpo-api-gateway 生产部署

### 9.1 是否必须

不是强依赖，但推荐在以下场景启用：

- 前端不希望直连多个后端
- 需要统一限流、超时、熔断
- 后续微服务数量增加

### 9.2 二进制安装

仓库已提供脚本：

```bash
cd /home/kali/ai_study/star-devops
bash scripts_dir/install-krakend-binary.sh
```

启动：

```bash
bash scripts_dir/start-cpo-api-gateway-binary.sh
```

校验：

```bash
bash scripts_dir/validate-cpo-api-gateway-binary.sh
```

### 9.3 systemd 建议

文件：`/etc/systemd/system/cpo-api-gateway.service`

```ini
[Unit]
Description=cpo-api-gateway
After=network.target

[Service]
Type=simple
User=starops
Group=starops

Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

## 10. 发布顺序建议

生产建议按以下顺序上线：

1. 中间件先到位：`MySQL -> Redis -> Nacos -> Elasticsearch`
2. `auth-all`
3. `AstrBot`
4. `cpo-ai-productivity-service`
5. 可选 `cpo-api-gateway`
6. 最后切前端 `Nginx`

## 11. 回滚策略
